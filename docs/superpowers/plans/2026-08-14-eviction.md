# Eviction Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release loaded rows to bound memory without disturbing heights, scroll position, selection or focus — the combination AG Grid's docs forbid.

**Architecture:** `resultMeta.window` already tells the engine the loaded span, so an absent row *outside* it is evicted and one *inside* it is deleted. Selection ranges become dataset-index spans under the existing honesty gate, so count is arithmetic and membership is containment. Heights survive via the tombstone cache that already exists; anchoring corrects only estimate drift, not eviction itself.

**Tech Stack:** TypeScript, vitest, Playwright (`apps/bench/tests/`), API Extractor.

**Spec:** `docs/superpowers/specs/2026-08-14-eviction-design.md`

**Depends on:** windowed data, merged in #375 — `leadingHeight`/`trailingHeight` and `resultMeta.window` are on main. Verify with `grep -c leadingHeight packages/layout-core/src/viewport-plan.ts` before starting; if it returns 0 you are on the wrong base.

### Task 2: Selection count over an unloaded span

**Files:**
- Modify: `packages/grid-core/src/indexed-selection.ts`
- Test: same file as Task 1

- [ ] **Step 1: Write the failing test**

Select a span of 4,901 rows, evict all but 30 of them, and assert the reported selection count is still **4,901** — computed with no rows loaded.

Then assert a rendered row inside the span paints selected (containment), and one outside does not.

- [ ] **Step 2: Run it, confirm it fails**

Expected: the count reflects only loaded rows.

- [ ] **Step 3: Implement**

Count is `Σ(hi − lo + 1)` over spans. Membership for a rendered row is containment on its dataset position. Neither loads rows.

**Do not** add an API that returns the selected *records* — that requires fetching and is explicitly out of scope.

**Inherited from Task 1 — read before implementing.** Task 1's retention rule is a *presumption*: a row absent from the snapshot is treated as deleted only when that can be **proven** (its last-known position, recovered from the previous snapshot and window, falls inside the current window). Otherwise it is presumed evicted and its range is retained. Three consequences land on this task:

1. **Phantom ranges exist.** Proof is unavailable when there is no previous window (the honesty gate has just started passing), and — the sharp case — **once a row has been absent for a single revision it can never again be proven deleted**, because the last committed snapshot no longer contains it. A row deleted server-side *while evicted* keeps its selection permanently. A window move concurrent with a deletion does the same.

   Today this is inert: `selectedCount` derives from the `selection.rows` program, not from `ranges`, and `indexedRangeContainsCell` returns `false` unless *both* endpoints resolve. **This task removes that safety net.** The moment count becomes `Σ(hi − lo + 1)` over spans, every phantom becomes a visible over-count of rows that no longer exist. Decide deliberately what the count does with an unprovable range, and pin it with a test.

2. **Retention is per-range; the spec's rule is per-row.** Task 1 retains only when *both* endpoints are unproven and drops when *either* is proven deleted — so a range whose start was genuinely deleted while its end was merely evicted is discarded whole, taking the evicted part with it. Dataset-index spans are the natural place to fix this: a deletion inside a span should narrow it, not destroy it.

3. **A retained range currently paints nothing** while either endpoint is unloaded, including for loaded rows in the middle of the span. Containment on dataset position is the designed fix — assert it directly.

**Also carried:** an evicted row that is the selection *anchor* still gets its anchor identity reassigned (`indexed-selection.ts`, `anchor = ranges[0]?.start ?? null` when the anchor is not visible). Task 1 added `expect(reconciled.anchor).toEqual(selection.anchor)` to hold the line; fixing it properly belongs with the focus work in spec §5.

- [ ] **Step 4: Verify, then prove it discriminates**

Reduce the span to 30 rows (all loaded). The count assertion must change accordingly — if 4,901 still passes, the test is reading something else.

- [ ] **Step 5: Commit**

```bash
git commit -m "feat(grid-core): selection count over an unloaded span

O(ranges), not O(selected rows)."
```

## Self-review

**Spec coverage.** §1 guarantees → Tasks 1–4. §2 spans → Tasks 1–2. §3 policy → **not covered**: this plan implements the *mechanisms* eviction needs, not the evictor itself. Block collapse beyond the tombstone bound is deliberately deferred — the spec calls it the least-designed part, and it should be specced separately once these mechanisms are proven. §4 anchoring → Task 3. §5 focus → **not covered**, see below.

**Known gaps, deliberate:**
- **No evictor.** Nothing in this plan actually releases rows; it makes releasing them *safe*. A consumer shrinking its window is the trigger, which the windowed-data contract already allows.
- **Focus (spec §5) is unimplemented here.** It needs the same treatment as selection and deserves its own task once Task 1's discriminator exists.

**Placeholders.** None. Tasks 1, 2 and 4 describe assertions rather than literal code because each depends on files the implementer must read first; each states what to assert and what must fail.

**Type consistency.** The window shape is `{ start, length }` in Tasks 1–2, matching `resultMeta.window`'s `{ start, hasMore }` plus `rows.length`.
