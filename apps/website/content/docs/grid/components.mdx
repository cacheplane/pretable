`@pretable/react` renders its own controls from a small component kit, and
ships those components for you to use and to replace. This page covers the
five that ship today: `PretableButton`, `PretableIconButton`,
`PretableSelect`, `PretableTextInput` and `PretableCheckbox`. Here is a grid
whose every labelled button is the app's own:

## The components

Four of the five render `<button type="button">`, always — a stray submit
inside your `<form>` is a real bug class, so `type` is not a prop on any of
them. `PretableTextInput` is the exception, and deliberately so: it is the
native `<input>`, where `type` is the whole point and passes straight
through. `className` and `style` pass straight through on all five — the
components set neither, so yours is the whole value — and each forwards its
`ref` to the node it renders. Select, TextInput and Checkbox compose that
ref with their internal node ref. Callback refs that return a cleanup function
have that cleanup called on detach or replacement; callbacks without one
receive `null`. Object refs are cleared on detach.

### Button

A labelled push-button in one of the grid's two looks.

| Prop      | Type                | Notes                                                                                       |
| --------- | ------------------- | ------------------------------------------------------------------------------------------- |
| `variant` | `"ghost" \| "link"` | `ghost` is the 24px action with a hover tint; `link` is plain accent text. Default `ghost`. |
| `site`    | `PretableSite`      | Where in the grid the button is; lands as `data-pretable-site`. Open to your own names.     |

### IconButton

An icon-only push-button. `aria-label` is **required** — it is the button's
only accessible name, and omitting it is a compile error rather than an
accessibility failure discovered later. An empty one warns once per page.

| Prop         | Type           | Notes                                                           |
| ------------ | -------------- | --------------------------------------------------------------- |
| `aria-label` | `string`       | Required. The accessible name.                                  |
| `site`       | `PretableSite` | Where in the grid the button is; lands as `data-pretable-site`. |

### Select

A select-only combobox: the kit's answer to the native `<select>`, whose open
list no theme can reach. The trigger is a `<button role="combobox">`; the list
is a portalled `role="listbox"` placed against it. `aria-label` is
**required**, for the same reason it is on `IconButton` — a picker with no
accessible name reads as an unnamed button — and an empty one warns once per
page. Four grid pickers are this component: the funnel menu's
[operator](/docs/grid/filtering#the-built-in-menu), the tool panel's
[filter-builder column and operator](/docs/grid/tool-panel#dom-hooks-and-strings),
and the grouping section's
[aggregate picker](/docs/grid/tool-panel#aggregates).

The keyboard is the listbox one: on a closed trigger, `↓`, `↑`, `Enter` or
`Space` opens the list; open, `↓` / `↑` move through it, wrapping at the ends
and skipping disabled options; `Home` / `End` jump to the first and last
enabled option; typing jumps by label prefix, the prefix resetting after
500ms of silence or when the list closes or reopens; `Enter` or `Space` commits the active option; `Escape`
closes the list and returns focus to the trigger; `Tab` closes it and moves
on. `onChange` fires only when the chosen value differs from `value`.

A `disabled` option is shown, skipped by the keyboard and inert to click —
that is how the aggregate picker shows a consumer-written custom aggregate it
must never write back. And a `value` that is absent from `options` renders as
its own label rather than as an empty trigger, so a picker never silently
disagrees with the state behind it.

Give every option a unique, stable `value`. If options change while the list
is open, the highlight follows that value through reordering. Removing or
disabling it moves the highlight to the first enabled option. An all-disabled
list has no highlight and cannot commit; an empty roster closes the list.
Adding options again does not reopen it.

String and number labels supply their own typeahead text. Rich labels require
`textValue`, the plain text to search; it can also override typeahead text for a
primitive label. The component does not inspect or render arbitrary React
components to discover their text. For example:

```tsx
const options = [
  { value: "open", label: "Open" },
  {
    value: "review",
    label: <strong>In review</strong>,
    textValue: "In review",
  },
];
```

When migrating rich options, add `textValue` to each label that is not a
string or number. `PretableSelectOption` is now a union type, so an interface
that previously extended it should use a type intersection instead, such as
`type AppOption = PretableSelectOption & { category: string }`.

```tsx
import { PretableSelect } from "@pretable/react";

<PretableSelect
  aria-label="Filter operator"
  options={[
    { value: "contains", label: "Contains" },
    { value: "equals", label: "Equals" },
    { value: "regex", label: "Matches regex", disabled: true },
  ]}
  value={operator}
  onChange={setOperator}
/>;
```

| Prop         | Type                              | Notes                                                                                                           |
| ------------ | --------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `options`    | `readonly PretableSelectOption[]` | The choices, in display order. Each has `value`, `label`, optional `disabled`, and `textValue` for rich labels. |
| `value`      | `string`                          | The committed value. Absent from `options`, it renders as its own label.                                        |
| `onChange`   | `(value: string) => void`         | Called with the chosen value, and only when it differs from `value`.                                            |
| `aria-label` | `string`                          | Required. The accessible name — name what it chooses, e.g. `Filter operator`.                                   |
| `site`       | `PretableSite`                    | Where in the grid the picker is; lands as `data-pretable-site`.                                                 |

### TextInput

A text field. It is the native `<input>` and nothing more — no wrapper
element, no clear button, no debounce — and that is the design rather than an
omission. The native element is the accessible one, so a screen reader, a
password manager and the platform's own autofill all keep working;
`type="date"` keeps its native picker and `inputMode` keeps the right soft
keyboard, neither of which survives a wrapper that reinterprets `type`. What
a theme needs from this control is the box, and that arrives through
`data-pretable-text-input`.

Every native input prop passes straight through — `type`, `inputMode`,
`value`, `onChange`, `placeholder`, `disabled`, `aria-*`, `className`,
`style` — which is why the table below has one row: `site` is the only prop
the component adds, and the rest are the native element's own. Value
semantics stay with the site rather than the component: the filter fields
[debounce their operand](/docs/grid/tool-panel#what-commits-and-when) and the
search box does not, and a component that owned that for all of them would be
wrong for most.

Seven grid fields are this component: the funnel menu's
[value field and its min/max pair](/docs/grid/filtering#the-built-in-menu),
the tool panel's
[filter-row value and its min/max pair](/docs/grid/tool-panel#dom-hooks-and-strings),
and the [columns search box](/docs/grid/tool-panel#the-columns-section).

The accessible name may come from an `aria-label`, an `aria-labelledby`, or a
`<label for>` naming its id. With none of the three it warns once per page —
an unnamed field reads as a bare edit box.

```tsx
import { PretableTextInput } from "@pretable/react";

<PretableTextInput
  aria-label="Filter value"
  type="date"
  value={value}
  onChange={(event) => setValue(event.target.value)}
/>;
```

| Prop   | Type           | Notes                                                                                           |
| ------ | -------------- | ----------------------------------------------------------------------------------------------- |
| `site` | `PretableSite` | Where in the grid the field is; lands as `data-pretable-site`. Every other prop is the input's. |

### Checkbox

A checkbox, drawn as a `<button type="button" role="checkbox">` carrying
`aria-checked` rather than as a native `<input type="checkbox">`. Three
things are plain on a button and a fight on an input: the mixed state
(`indeterminate` is a DOM property with no attribute at all), the roving
`tabIndex` a control inside a body cell needs, and a tick that takes the
theme's tokens — the user agent owns the native one until `appearance: none`
throws the whole control away. So the glyph is the kit's own: the check icon
when `checked` is `true`, a minus when it is `"mixed"`, nothing when `false`.

It is controlled. `onCheckedChange` is called with the next value and
nothing is written until you write it, and `"mixed"` toggles to `true` — the
header select-all's "some rows, not all" resolving to "all". The keyboard is
the native button's, so `Space` and `Enter` both activate and both arrive as
a click; there is no key handler of its own to disagree with the platform. A
consumer `onClick` runs **first** and may `preventDefault()` to veto the
toggle, which is how a shift-click range select keeps the click without a
second write following it. Native button props pass through — `disabled`,
`tabIndex`, `aria-busy`, `aria-invalid`, `aria-errormessage`.

Seven grid controls are this component: the
[row-select header and cell checkboxes](/docs/grid/selection#checkbox-column),
the [boolean cell](/docs/grid/editing#booleans), the
[column visibility toggle](/docs/grid/tool-panel#the-columns-section), the
[hide-grouped switch](/docs/grid/tool-panel#hide-grouped-columns), and the
enum checklists in the [funnel menu](/docs/grid/filtering#the-built-in-menu)
and the [tool panel's filter row](/docs/grid/tool-panel#rows-runs-and-the-join).

An `aria-label` names it, and so does a wrapping `<label>` — a `<button>` is
a labelable element, so the text names the control and clicking that text
toggles it, which is the shape the hide-grouped switch uses. With neither it
warns once per page, the way `IconButton` does.

```tsx
import { PretableCheckbox } from "@pretable/react";

<label>
  <PretableCheckbox checked={hideGrouped} onCheckedChange={setHideGrouped} />
  Hide grouped columns
</label>;
```

| Prop              | Type                      | Notes                                                                 |
| ----------------- | ------------------------- | --------------------------------------------------------------------- |
| `checked`         | `boolean \| "mixed"`      | The state. `"mixed"` draws the minus glyph and toggles to `true`.     |
| `onCheckedChange` | `(next: boolean) => void` | Called with the next value after a click, before anything is written. |
| `site`            | `PretableSite`            | Where in the grid the checkbox is; lands as `data-pretable-site`.     |

## Styling

The styling channel is the one the whole grid uses: attributes and tokens.
Every push-button carries `data-pretable-button` or
`data-pretable-icon-button`; a labelled button also carries
`data-pretable-variant`, and any of them carries `data-pretable-site` when
the grid gave it one. A select's trigger carries `data-pretable-select` and
writes its committed value to `data-pretable-value` — a `<button>` has no
`.value`, so that attribute is the truth a test reads and a selector
matches. Its label span is `data-pretable-select-label`; the open list is
`data-pretable-listbox` with a `data-pretable-option` per entry, each
carrying its own value as `data-pretable-option-value` — which option it
**is**, as against the trigger's one committed `data-pretable-value` — the
keyboard-active one carrying `data-active` and the chosen one
`aria-selected="true"`. A text field carries `data-pretable-text-input`, and
a checkbox `data-pretable-checkbox` plus the `aria-checked` its three states
live in: match `[aria-checked="true"]` and `[aria-checked="mixed"]` rather
than a `:checked` pseudo-class, which a `<button>` never has. The grid's own
sites also keep their original attribute (`data-pretable-filter-clear`,
`data-pretable-tool-reset`, `data-pretable-row-select`, …), so a selector you
already wrote keeps matching.

```css
[data-pretable-button][data-pretable-variant="ghost"] {
  --pretable-accent: rebeccapurple;
}
[data-pretable-site="tool-reset"] {
  color: var(--pretable-text-error);
}
[data-pretable-select][data-pretable-value="between"] {
  font-variant-numeric: tabular-nums;
}
[data-pretable-option][data-active],
[data-pretable-option][aria-selected="true"] {
  background: var(--pretable-bg-hover);
}
[data-pretable-text-input][data-pretable-site="filter-value"] {
  font-variant-numeric: tabular-nums;
}
[data-pretable-checkbox][aria-checked="mixed"] {
  --pretable-checkbox-checked-bg: var(--pretable-accent);
}
```

## Replacing a component

Pass `components` to `<PretableSurface>` (or `<Pretable>`) with one entry per
component type you want to replace. The replacement is used everywhere that
type appears — the tool panel and the portalled filter dialog for `Button`;
the header, the tool panel and the group panel for `IconButton`; the filter
dialog, the filter builder and the grouping section for `Select`; the funnel
menu's operand fields, the filter builder's operand fields and the Columns
search box for `TextInput`; the row-select column, the boolean cell, the tool
panel and both enum checklists for `Checkbox` — and receives exactly the props
the built-in does, `site` included, so it can branch on where it is.

| Prop         | Type                          | Notes                                                                          |
| ------------ | ----------------------------- | ------------------------------------------------------------------------------ |
| `Button`     | `PretableButtonComponent`     | Receives `PretableButtonProps`; must forward its `ref` to the button node.     |
| `Checkbox`   | `PretableCheckboxComponent`   | Receives `PretableCheckboxProps`; must forward its `ref` to the button node.   |
| `IconButton` | `PretableIconButtonComponent` | Receives `PretableIconButtonProps`; must forward its `ref` to the button node. |
| `Select`     | `PretableSelectComponent`     | Receives `PretableSelectProps`; must forward its `ref` to the button node.     |
| `TextInput`  | `PretableTextInputComponent`  | Receives `PretableTextInputProps`; must forward its `ref` to the input node.   |

Forwarding the `ref` is the one obligation on a replacement: the grid anchors
menus on the node and returns keyboard focus to it — a replaced `Select`
owes it too, because the filter dialog focuses its operator picker when it
opens. The grid takes no ref to a field or a checkbox today, so a replaced
`TextInput` or `Checkbox` owes the ref as a contract rather than to a live
caller — it is the handle anything reaching the real node goes through, and a
replacement that swallows it cannot be given one later. Under React 18 that
means `forwardRef`; under React 19 a plain `ref` prop is enough. The set of
built-in `site` names is the
`PretableBuiltInSite` type and grows additively — a new grid control
may introduce a new site without a major bump.
