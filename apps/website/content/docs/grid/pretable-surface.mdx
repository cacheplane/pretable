`<PretableSurface>` is the unopinionated grid component. Same engine as [`<Pretable>`](/docs/grid/pretable-component), but every prop is yours to set. The website's homepage hero and the bench harness both render this component directly — what we measure is what you ship.

```tsx
import { PretableSurface, type PretableColumn } from "@pretable/react";

interface Event extends Record<string, unknown> {
  id: string;
  timestamp: string;
  kind: string;
  message: string;
  status: "ok" | "warn" | "error";
}

const columns: PretableColumn<Event>[] = [
  { id: "timestamp", header: "Time", widthPx: 92, pinned: "left" },
  { id: "kind", header: "Kind", widthPx: 180 },
  { id: "message", header: "Message", widthPx: 420, wrap: true },
  { id: "status", header: "Status", widthPx: 80 },
];

export function EventStream({ events }: { events: Event[] }) {
  return (
    <PretableSurface<Event>
      ariaLabel="Live event stream"
      columns={columns}
      getRowId={(row) => row.id}
      rows={events}
      viewportHeight={520}
    />
  );
}
```

## When to use this vs `<Pretable>`

| You want…                                                                              | Reach for                                     |
| -------------------------------------------------------------------------------------- | --------------------------------------------- |
| A grid in 3 props, sensible defaults                                                   | [`<Pretable>`](/docs/grid/pretable-component) |
| Custom cell renderers, telemetry, controlled interaction state, or fine-grained sizing | `<PretableSurface>`                           |
| To drive everything yourself with hooks                                                | [`usePretable`](/docs/grid/custom-rendering)  |

`<Pretable>` is a thin wrapper around `<PretableSurface>` with a hardcoded `viewportHeight={320}`, hardcoded cell renderers, and no way to reach telemetry, filtering, or controlled state. If any of that doesn't fit, drop down to the surface.

## Server-applied filtering and sorting

_@experimental — the four props in this section are new, and their shape may change across minor releases._

By default the engine owns the whole row model: you hand it rows, it filters them, sorts them, and counts them. That breaks down when the dataset is too large to ship to the browser. Then a server does the filtering and sorting, sends back a page of results, and the grid's job changes: **display** the filter and sort state without applying it, and stop implying that the rows it holds are the whole story.

`processing` is where you say who does what:

```tsx
<PretableSurface<Trade>
  ariaLabel="Trades"
  columns={columns}
  dataState={dataState}
  getRowId={(row) => row.id}
  onFiltersChange={(filters) => refetch({ ...query, filters })}
  onSortChange={(sort) => refetch({ ...query, sort })}
  processing={{ filter: "external", sort: "external" }}
  resultMeta={{ total: { kind: "exact", count: 5432 }, datasetKey: query.id }}
  rows={page}
  viewportHeight={520}
/>
```

Nothing about the controls changes. Under `filter: "external"` the funnel menu still opens, still shows which operator is applied, still fires `onFiltersChange`; under `sort: "external"` the header still cycles and still fires `onSortChange`. What changes is the derivation: the engine leaves the loaded rows in the order they arrived and passes them through unfiltered. Those callbacks are your cue to issue the next query and land the answer with `rows`.

Two things to pair with it. Give server-filtered columns a [`filterOperators`](/docs/grid/api-reference#pretablecolumntrow) list so the menu only offers operators your query language can honor, and keep `sortable: false` on columns the server cannot order by — sanitization works exactly as it does locally, which is how you declare a column unsortable.

This is also where [row identity](/docs/grid/api-reference#row-identity) earns its keep. Every answer lands as a wholesale `rows` replacement in a different order, so selection, focus and an open editor survive it only because they are keyed by an id the server sends back with the row. Make sure the id your `getRowId` reads is one the query layer preserves across pages and re-sorts.

`processing` is create-time configuration, like `autosize`: changing it rebuilds the grid and discards selection, focus, measured row heights, column layout, and any edit in flight. Decide it once per grid. Only its two fields are read, so an inline object literal is safe.

### Totals and dataset identity

Under external filter authority the grid cannot count what matches — it never saw the rows that didn't come back. `resultMeta.total` is you telling it:

| Total                           | Use it when                                                                                                       |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `{ kind: "exact", count }`      | the count is authoritative. The only kind that can be published as `aria-rowcount`.                               |
| `{ kind: "estimate", count }`   | the count is approximate. Announced in prose ("about 5,000"), never through an attribute whose contract is exact. |
| `{ kind: "unknown", atLeast? }` | the store won't say (Elasticsearch's `gte 10000`, an unbounded cursor). `atLeast` is a floor, if you have one.    |

The total is what makes every count in the UI honest. It decides whether ticking the header checkbox announces "all rows" or a loaded-window figure, whether a copy is described as scoped, and whether `aria-rowcount` reports the population or just the rows in the model. Omit it under external filtering and the grid assumes the worst: `unknown`, and every label goes loaded-scope.

Global `aria-rowindex` values — a row that says "42 of 5,432" instead of "42 of 200" — depend on a contract you have to keep: **the loaded rows must be a contiguous window starting at the first matching row.** Head-anchored paging (fetch 200, fetch 200 more, append) keeps it; jumping to an arbitrary offset does not. Where the grid can detect a violation it downgrades to loaded-model counts rather than publish a wrong position, and dev-warns. Grouping, engine sort authority over a partial window, and a non-`exact` total each trigger the same downgrade — the population figure then lives in the announcements and in your own chrome, which is a fine place for it.

`resultMeta.datasetKey` names the dataset the loaded rows came from. Change it and the engine treats what arrives as answering a **different question**: selection, focus, group-expansion overrides, any in-flight edit, and the previous total are dropped, rather than silently re-pointed at whatever now occupies those row ids. Keep it stable while paging deeper into one result set; change it whenever the query changes. A grid that never sets it behaves exactly as it always has.

The pivot outranks controlled state. If you drive [`state.selection`](#props) and the same value comes back on the render that pivots, the grid holds the clear instead of letting the re-assert undo it — a selection minted before the pivot is indistinguishable from one you meant to keep. Take control again by supplying a selection minted for the new dataset.

### The data lifecycle

`dataState` is the phase you assert; the grid renders it and never infers it. There is no default, and that is deliberate: a grid that is not given the prop shows no body blocks, makes no phase announcements, and sets no phase attribute. Local and streaming grids are untouched. A remote consumer supplies it from the first render, usually starting at `{ phase: "loading" }`.

| Phase          | Means                                                            | With rows loaded                                  | With nothing loaded |
| -------------- | ---------------------------------------------------------------- | ------------------------------------------------- | ------------------- |
| `idle`         | the loaded rows answer the query you want                        | rows                                              | empty block         |
| `loading`      | nothing usable is loaded for the query you want                  | —                                                 | loading block       |
| `stale`        | the rows answer a _previous_ query; the current one is in flight | rows stay visible and interactive                 | loading block       |
| `refreshing`   | same query, a newer fulfillment in flight (polling)              | rows stay visible                                 | empty block stays   |
| `loading-more` | a tail extension is in flight                                    | rows stay visible                                 | —                   |
| `error`        | the fetch failed; `message` is yours to supply                   | rows stay visible, with an error strip above them | error block         |

The rule running through that table is that fulfilled rows are never discarded to show a status. A failed refresh leaves you looking at the last good results with a strip explaining the failure, not an empty grid. A 2-second poll over an empty result does not flicker empty → loading → empty.

The phase reaches CSS as `data-pretable-data-phase` on the grid root — that is the hook for dimming stale rows — and each block carries `data-pretable-body-state` (`"loading"`, `"empty"`, `"error"`, `"error-strip"`). Assistive technology hears the phase through the grid's existing polite live region: a count when a load settles ("Showing 200 of 5,432"), a notice on going stale, the error message on failure. All of that text is overridable through [`messages`](#props).

`renderBodyState` replaces what goes inside those blocks — the wrapper and its data attribute stay, so your styling hooks survive:

```tsx
<PretableSurface
  dataState={dataState}
  renderBodyState={({ kind, errorMessage, loadedRowCount, matchingTotal }) =>
    kind === "error-strip" ? (
      <>
        <span>{errorMessage ?? "Couldn't refresh."}</span>
        <button onClick={retry} type="button">
          Retry
        </button>
      </>
    ) : kind === "empty" ? (
      <p>No trades match this filter.</p>
    ) : null
  }
  /* ... */
/>
```

Branch on `kind`, not on the phase and the counts: a retry button belongs in the `"error-strip"` that sits above intact rows, and re-deriving that distinction is work the grid has already done. Returning `null` falls back to nothing, not to the built-in — return the built-in's text yourself if you only want to restyle one block.

Load-more and retry controls that are not part of a block belong outside the grid element. The row model holds no synthetic loading or footer rows: one would take an `aria-rowindex` that belongs to a real row, and would then need exemptions from focus, selection, and copy.

## Telemetry

`onTelemetryChange` is how you observe the grid from outside React renders. The shape:

```ts
interface PretableTelemetry {
  focusedRowId: string | null;
  rowModelRowCount: number; // post-filter
  renderedRowCount: number; // currently in DOM
  selectedRowId: string | null;
  loadedRowCount: number; // pre-filter
  totalHeight: number; // virtualized scroll height (px)
  visibleRowCount: number;
  visibleRowRange: { start: number; end: number };
}
```

**Stability is critical.** If you pass an inline arrow like `onTelemetryChange={(t) => setX(t)}`, the effect that dispatches it refires every render — combined with `setX` triggering a re-render, you can hit "Maximum update depth exceeded." Use `useCallback` with a ref:

```tsx
const telemetryRef = useRef<PretableTelemetry | null>(null);
const onTelemetryChange = useCallback((t: PretableTelemetry) => {
  telemetryRef.current = t;
}, []);
```

If you only need fps / frame timing, measure those with `requestAnimationFrame` deltas in a separate hook (the website's `useFrameStats` is the model).

## Streaming example

The website's homepage hero is a `<PretableSurface>` driven by a `requestAnimationFrame` loop with batched `setRows`. Same pattern, simplified:

```tsx
import { useEffect, useRef, useState } from "react";
import { PretableSurface, type PretableColumn } from "@pretable/react";

interface Row extends Record<string, unknown> {
  id: string;
  message: string;
}

const columns: PretableColumn<Row>[] = [
  { id: "id", header: "ID", widthPx: 80 },
  { id: "message", header: "Message", widthPx: 480, wrap: true },
];

export function StreamingGrid() {
  const [rows, setRows] = useState<Row[]>([]);
  const seqRef = useRef(0);

  useEffect(() => {
    let raf = 0;
    let pending: Row[] = [];

    const tick = () => {
      // produce ~16 events per frame at 60fps = ~1k/sec
      for (let i = 0; i < 16; i++) {
        const seq = seqRef.current++;
        pending.push({ id: `seq-${seq}`, message: `event #${seq}` });
      }

      if (pending.length > 0) {
        const batch = pending;
        pending = [];
        // Single setState per frame — batching matters for high rates
        setRows((prev) => [...batch.reverse(), ...prev].slice(0, 200));
      }

      raf = requestAnimationFrame(tick);
    };
    raf = requestAnimationFrame(tick);
    return () => cancelAnimationFrame(raf);
  }, []);

  return (
    <PretableSurface<Row>
      ariaLabel="Streaming demo"
      columns={columns}
      getRowId={(row) => row.id}
      rows={rows}
      viewportHeight={520}
    />
  );
}
```

Key tips:

- **Batch setState per frame.** The hero's homepage demo emits 1k events/sec; one setState per emission would burn the page. One per `requestAnimationFrame` is safe.
- **Cap the buffer.** Sliding window of `~200` rows keeps memory + render cost bounded while still feeling alive.
- **Use `wrap: true`** on text columns — multi-line cells with variable heights are the wedge. The grid's measurement reconciliation handles them without layout thrash.

## Sibling preset

`@pretable/react` ships one more opinionated preset on top of `<PretableSurface>`:

- **`<LabeledGridSurface>`** — renders each cell as a label above its value instead of a bare value, forwards `locale` for [native number formatting](/docs/grid/number-formatting), and gives you class-name hooks (`labelClassName`, `valueClassName`, `bodyCellClassName`, `headerCellClassName`, `rowClassName`, `pinnedClassName`) plus a `formatValue` override. The override receives raw `value` and the surface's resolved `formattedValue`; `column.render` wins over the wrapper, while the wrapper uses `formatValue` when present and `formattedValue` otherwise. Good for log- or record-style data where a cell means nothing without its field name. It ships no CSS of its own — the layout is yours to write against those class names.

If your rows read as `{label, value}` pairs, start with `<LabeledGridSurface>`. Otherwise the bare `<PretableSurface>` is the right primitive.
